# Security Policy

## Status: pre-alpha — do not put real authority behind this

Protocol version `0.1` is not stable. Event shapes, reason codes, and
verification semantics may still change without a migration path. Nothing here
has been independently audited.

Do not use LineageAuth as the sole control on a consequential action.

## Never send us key material

Do not include in a report, an issue, a pull request, a screenshot, or a test
case:

- Ed25519 private seeds
- JWK `d` values
- wallet seed phrases or private keys
- recovery private keys
- API secrets, OAuth refresh tokens, or bearer tokens

If a report needs a signing key to reproduce, derive a throwaway one and say so.
The test keys in this repository are derived from a public constant and are
unsafe by construction — reuse those.

**If you believe a private key has been exposed anywhere in this project,
rotate it first and report second.** A key is compromised the moment it is
published; a report does not un-publish it.

## Reporting a vulnerability

Use GitHub's private vulnerability reporting on this repository
(**Security → Report a vulnerability**). That keeps the report private until a
fix exists.

Please do not open a public issue for anything that lets someone forge
authority, bypass revocation, or replay an approval.

Useful reports include: what an attacker controls, what they gain, and a
minimal reproduction — ideally a signed event bundle and the verification
command that returns the wrong answer.

## In scope

The things this protocol exists to prevent:

- forging or altering a signed event without invalidating its proof
- constructing a delegation that grants more than its parent held
- using a revoked, expired, or superseded grant
- replaying a human approval receipt, or binding one to a different action,
  destination, or payload
- satisfying a recovery quorum with duplicate signers, non-members, or fewer
  signatures than the threshold
- making an unsigned claim authoritative through an index, cache, resolver, or
  chat message
- causing the verifier to accept an unknown version, unknown event type, or
  unsupported DID method instead of failing closed
- canonicalization ambiguity: two byte strings that should not verify under one
  signature, or one payload with two valid encodings

Also in scope: any way to make the CLI, library, or adapters touch the network,
read a private key, or perform an external write when they should not.

## Out of scope

- **A valid signature meaning something it does not.** A `did:key` proves
  control of a key. It is not identity, affiliation, employment, honesty, or
  safety. The verifier saying `SIGNATURE_VERIFIED` for a key you dislike is
  correct behaviour.
- **Sybil resistance.** Fleet disclosure is voluntary. Undisclosed fleets are a
  documented limitation, not a bug.
- **Attestation truthfulness.** An attestation proves who signed an opinion, not
  that the opinion is correct.
- **Technocore durability or trustworthiness.** It is transport and discovery,
  never a source of truth, and all of its content is untrusted data.
- Reports generated by a scanner with no demonstrated impact.

See [docs/28_NON_GOALS_LIMITATIONS.md](docs/28_NON_GOALS_LIMITATIONS.md) for the
full list of things this protocol does not claim.
